Life Guard System Engineering Report Section 1: Overview

01. Executive Summary & Problem Space

Personal physical safety remains one of the most critical challenges of modern urban life. Millions of individuals—including night-shift professionals, solo commuters, students, and lone travelers—routinely traverse precarious environments where sudden aggression, medical emergencies, or unexpected transit deviations can threaten life within seconds.

While dozens of consumer "safety apps" exist on app stores, real-world deployment data reveals that conventional safety software consistently experiences catastrophic failure during actual distress events. These failures stem from three systemic architectural flaws:

Critical Flaw 1 Physical Incapacitation

Standard apps expect a victim who is being assaulted, physically restrained, or fleeing to unlock their phone, launch an app, tap a button, and confirm a dialog. In reality, fine motor control is lost under adrenaline surges, and physical phones are frequently snatched, dropped, or trapped in pockets.

Critical Flaw 2 Carrier & SMS Fragility

Safety apps often rely exclusively on cellular SMS. On modern prepaid mobile plans (especially across global markets like India), outgoing SMS is routinely blocked if the user lacks an active recharge package. Furthermore, modern Android (API 33+) flags sideloaded safety apps under "Restricted Settings", completely blocking SMS.

Critical Flaw 3 Proprietary API Hard Stops

Commercial applications tightly bind their mapping services to proprietary clouds (e.g. Google Maps SDK). When cloud credit quotas expire or keys fail, map views become blank gray canvases, rendering deviation algorithms completely blind.

Life Guard Solution Zero-Tolerance Architecture

Life Guard is engineered around zero-click triggers, triple-redundant communication channels (Direct Call + WhatsApp + SMS), native open-source 2D mapping (osmdroid), and autonomous accessibility auto-clickers that bypass all human confirmation requirements.

⚠️ The Core Engineering Mandate
If an alert requires the victim to look at the screen, confirm an action, or press a send button, the system has failed. Life Guard executes distress operations autonomously at the hardware level in under 100 milliseconds.

02. System Architecture & Topologies

Life Guard implements a decoupled, fault-tolerant dual-layer architecture consisting of an Android Native Client operating alongside a High-Concurrency Cloud Geospatial Backend.

03. Core Subsystems & Technical Mechanics

3.1. Guard Mode: Dead-Man Switching & Panic Accelerations

Guard Mode is an active defense state initiated when traversing hazardous sectors. The user maintains continuous thumb pressure on the central shield interface.

  • Dead-Man Switch Mechanics: If physical force causes the user's finger to separate from the glass (e.g., phone knocked away, physical struggle), a high-urgency 5-second countdown triggers with escalating dual-frequency vibration pulses. If the user does not enter their offline-salted PIN within 5 seconds, silent automated SOS dispatch activates across all channels.
  • Double-Tap Panic Trigger: Two consecutive taps registered within 350ms bypass all grace periods and immediately fire maximum-priority distress signals.

3.2. Check-In Safety Timer & Keyguard Overlay

To prevent phone OEM background task killers from terminating countdowns, Life Guard utilizes Android's AlarmManager.setExactAndAllowWhileIdle(). Upon timer expiration:

  1. A partial WakeLock acquires CPU execution and turns the physical screen on via FLAG_TURN_SCREEN_ON.
  2. TimerCheckInActivity renders directly above the Android lockscreen using FLAG_SHOW_WHEN_LOCKED.
  3. A 15-second grace countdown initiates with 1000ms acoustic-vibrational warnings. Failure to authenticate with the stored SHA-256 PIN executes distress dispatch.
Life Guard System Engineering Report Section 4: Geospatial Routing

04. Open-Source Geospatial & Deviation Engine

A foundational innovation in Life Guard v5.0+ was the complete elimination of proprietary, paywalled mapping platforms. By embedding the osmdroid OpenStreetMap Android Native SDK (6.1.18), Life Guard achieves 100% free, offline-cached, high-performance mapping with zero API keys and zero cloud quotas.

Routing Pipeline 1 Google Maps Interception

Users navigate in their standard Google Maps app, tap "Share directions", and choose Life Guard. RouteImportActivity catches the share intent, follows HTTP redirect hops to resolve shortlinks (maps.app.goo.gl), parses geographic coordinates via regex, and requests routing geometry from OSRM.

Routing Pipeline 2 120Hz Freehand Finger Draw

In RouteScreen.kt, users tap "✏️ Draw Route" and drag their finger across streets or informal trails. A Jetpack Compose hardware-accelerated Canvas tracks touch gestures at 120Hz, rendering a glowing neon red corridor (`#FF1744`) and projecting screen pixels into geographic GeoPoint coordinates.

4.1. Cross-Track Route Deviation Algorithm

To detect if a user has been diverted or kidnapped, RouteDeviationService continuously evaluates incoming GPS fixes against the defined polyline path.

📐 Mathematical Deviation Formulation
Given user location $p$ and a route line segment $s = (a, b)$, the orthogonal projection factor $t$ is: 
t = ((p.lat - a.lat)*(b.lat - a.lat) + (p.lon - a.lon)*(b.lon - a.lon)) / distance_sq(a, b)
The true cross-track spatial distance is then evaluated using spherical Haversine projection: 
distance_to_segment = Haversine(p, a + clamp(t, 0.0, 1.0) * (b - a))

If $\min(\text{distance}) > 150\text{ meters}$, a 15-second grace window begins. If the user remains off-route and fails to disarm the alert with their PIN, an Off-Route Deviation SOS is triggered automatically.

05. 0-Click Accessibility Automation

WhatsApp is the primary real-time communication platform globally, making it the most effective distress recipient. However, WhatsApp’s security model strictly prohibits third-party Android apps from sending messages silently in the background. Standard Android intents merely open the chat with pre-filled text, requiring a physical tap on the green send button—an impossible requirement for an incapacitated victim.

Life Guard solves this through an official Android AccessibilityService implementation (LifeGuardAccessibilityService.kt):

Stage Component Execution Logic & Technical Operation
1. Arming EmergencyCallHelper Upon SOS trigger, LifeGuardAccessibilityService.armAutoSend() activates an internal 15-second auto-click window.
2. Intent Launch Android OS Intent Launches target URI https://api.whatsapp.com/send?phone=+91...&text=... with live Google Maps tracking coordinates.
3. Window Detection AccessibilityService Listens for TYPE_WINDOW_STATE_CHANGED from com.whatsapp or com.whatsapp.w4b.
4. Node Tree Scan Node Inspector Recursively scans the active view hierarchy for resource IDs com.whatsapp:id/send and content descriptions matching "Send".
5. Click Injection AccessibilityNodeInfo Executes ACTION_CLICK on the clickable parent container in < 100 milliseconds.
6. Auto-Return Global Action Manager Disarms the listener and immediately invokes performGlobalAction(GLOBAL_ACTION_BACK), returning the user to safety.
Life Guard System Engineering Report Section 6: Cloud API & Schemas

06. Database Schema & Cloud Endpoints

The backend infrastructure is hosted on Render and backed by Neon Serverless PostgreSQL. All endpoints enforce strict data typing via Pydantic schemas.

6.1. Core PostgreSQL Schemas

-- Users Table
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    phone_number VARCHAR(20) UNIQUE NOT NULL,
    hashed_password VARCHAR(255) NOT NULL,
    pin_hash VARCHAR(255) NOT NULL,
    emergency_contact_phone VARCHAR(20),
    is_helper BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Emergency Alerts Table
CREATE TABLE alerts (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id) ON DELETE CASCADE,
    alert_type VARCHAR(50) NOT NULL, -- 'PANIC_DOUBLE_TAP', 'DEAD_MAN_RELEASE', 'ROUTE_DEVIATION', etc.
    latitude DOUBLE PRECISION NOT NULL,
    longitude DOUBLE PRECISION NOT NULL,
    status VARCHAR(20) DEFAULT 'ACTIVE', -- 'ACTIVE', 'RESOLVED', 'FALSE_ALARM'
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

6.2. RESTful API Specification

Method Endpoint Payload Summary System Behavior
POST /api/v1/auth/register {full_name, phone, password, pin} Hashes credentials with bcrypt & SHA-256; generates JWT session.
POST /api/v1/auth/login {phone_number, password} Authenticates user and returns Bearer token.
POST /api/v1/location/update {user_id, latitude, longitude} Records real-time GPS telemetry in geospatial database.
POST /api/v1/alerts/trigger {user_id, alert_type, lat, lng} Creates alert record, queries nearby helpers, dispatches high-priority FCM.
POST /api/v1/alerts/resolve {alert_id, pin} Validates PIN; cancels active emergency broadcast state.
